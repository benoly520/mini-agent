## 二、卡点一：「Agent」这个词在你的项目里有 5 种含义

这是你混乱的最大来源。同一个词指五种东西，每一种的能力边界完全不同：

| 你代码里的名字 | 实质是什么 | 有独立模型循环吗 | 能改管家状态吗 |
| --- | --- | --- | --- |
| `MainAgent`（`core/core/main-agent.ts`） | **维修业务的编排对象**，一个带状态机的普通类，`role='orchestrator'` 但内部没有一次 LLM 调用 | ❌ | ✅ 它自己管工单 |
| `TaskEngine` + `runner.ts` 的模型循环 | 真正的「模型 Agent」：问模型→校验→执行→回喂 | ✅ | 受护栏约束 |
| `DelegateRunner` 创建的研究子任务 | 真正的**独立模型循环**子 Agent，新任务 ID / 新上下文 / 工具白名单 / 共享预算 | ✅ | ❌ 只回传结果 |
| `AgentPlugin`（Domain/Provider/Channel） | 大多是**确定性业务能力**，契约只要求 `async handle()`，不要求模型 | ❌ | ❌ |
| 专业 Agent（物业 / 五金店，独立进程） | 通过 HTTP JSON 协议接入的**外部 Agent**，各自有 4 轮循环 | ✅（各自进程） | ❌ 写工具只出提案 |

**你现在明白为什么「主 agent / subagent」讲不清了吗？** 因为「主 Agent」在两个场景里指两个不同的类：维修链路指 `MainAgent`（无模型循环），通用任务链路指父 `TaskEngine`（有模型循环）。你的 013 第 83 行写「所有任务统一经过 MainAgent：尚未统一」——这就是两套入口的历史包袱，不是你理解力的问题。

> **一句话心法**：判断一个东西是不是 Agent，只看三件事——有没有自己的模型循环、有没有独立上下文、有没有自主决策下一步的权力。名字一概不作数。

## 三、卡点二：function call 里的「推理」到底是谁在做

你实现了「原生 `tools` + JSON 兜底」双协议，`LLM_PROTOCOL=auto`，E2E 里 3/0、5/0 全是 native。你没完全理解的，可能是这三个问题：

**1. `reasoning_content` 是你的模型在「思考」吗？**
不是。GLM-4.5-Flash 是快思考模型，`reasoning_content` 在你的 017 第 24 行被当作 `thought` 展示，但它更接近「模型对当前动作的自然语言说明」，不是真正的链式推理。**真正的「推理」发生在 token 预测里**：模型在「工具描述 + 当前上下文」条件下，预测下一个最可能的 token 恰好是工具名和参数。它并没有一个脱离语言的「思考部门」。

**2. 为什么要留 JSON 兜底？**
因为原生 tool calling 是厂商**额外训练**出来的能力，不是语言模型天然具备的。你 017 第 104-105 行已经记录了 GLM-4.5-Flash「偶发只回正文」。兜底不是你的实现不优雅，是对抗概率性的必要冗余——这一层你已经做对了。

**3. 为什么「拍板权在代码」是对的？**
你在 016 第 129 行写了「思考可见，拍板在代码」，在 013 第 222 行说这点「强于多数只靠提示词约束的示例实现」。为什么强？因为**模型输出是概率的，而授权、额度、付款是二值的**。让概率系统做二值决策，迟早出事。你把它做成了确定性护栏 + 两阶段确认，这是生产级 Agent 的正确形态。

> **一句话心法**：模型负责「看起来该做什么」，代码负责「实际上允许做什么」。你的架构已经这么做了，只是还没把它内化成直觉。

## 四、卡点三：你追的「Collaborator Workers」其实是个幻影

你提到「cobaratoer Workes」——按你项目语境，应该是 coordinator-worker / collaborator workers 这一类多智能体模式。

**你的 `doc/013` 第 9.5 节已经给出了正确答案**：

> - 对等 collaborator 网络：私人管家产品更需要单一主协调者，不需要多个 Agent 自由协商。
> - 并行与后台：只有在长任务、并行研究真正出现时才值得增加，否则只是为形式引入复杂度。
> - 强沙箱隔离：当前插件都是可信内置实现，工具白名单够用。

也就是说：**你已经在「架构思想层基本对齐，核心骨架层对齐度较高」（013 §9.4），你追的那个「完全体 collaborator workers」不是缺口，是被多智能体名词制造出来的焦虑。**

car 你真的在追的东西，其实是 013 §9.3 表格里的几行——并行 fan-out、后台任务、统一调度抽象、跨会话记忆。这些是**运行时成熟度**问题，不是「理解不够」问题。你不理解的是「为什么我照着前沿模式做了却还是觉得不完整」，答案是：**前沿模式本身就是为不同场景设计的**，OpenAI 的 handoff、AutoGen 的 group chat、CrewAI 的 crew 各有适用面，而你的私人管家场景恰好不需要其中大部分。

## 五、真正的补课方式：两个仓库联动

你之前把 mini-agent 当成「起点」，把 alter-ego 当成「终点」。换一个心智模型：

- **mini-agent = 显微镜 / 受控实验台**：200 行、零依赖、无护栏无插件无持久化，任何一个概念都能隔离成 30-50 行看懂
- **alter-ego = 战场**：真实业务、真实模型、真实复杂度，用来验证实验结论

**仅靠读 alter-ego 的代码永远「想不通」，因为它把 10 个概念叠在了一起。回 mini-agent 把每个概念单独跑一遍，再回来看 alter-ego，会有「啊原来如此」的感觉。**

### 三个最小实验（建议按此顺序，每个都能独立跑通并提交）

| 实验 | 在 mini-agent 里做什么 | 验证完回 alter-ego 看哪里 | 解开哪个困惑 |
| --- | --- | --- | --- |
| **① 委派即工具** | 加一个 `delegate` 工具：主循环调用它时，new 一个全新的 `history=[]`，只给 1-2 个只读工具，跑一轮后把结果作为 tool 消息回传 | `delegation.ts`、`task-engine.ts` 的 `delegate_research` | subagent 到底是什么 / 为什么委派在模型眼里只是一次工具调用 |
| **② 双协议对照** | 把 `tools` 参数去掉，改成 system prompt 里写「请输出 JSON」，自己解析；再切回原生 `tool_calls`，对比两种失败模式 | `provider.ts` 的原生 tools + `interpret.ts` 的 JSON 兜底 | function call 的推理本质 / 为什么必须留兜底 |
| **③ 写工具只出提案** | 加一个 `write_note` 工具：调用时不直接写文件，只返回「提案 + 参数摘要」；主循环等用户输入 y/n 才真正执行 | `guardrails.ts`、`write-policy.ts`、`runner.ts` 的 `onHandoff` | 为什么拍板权不能给模型 / 两阶段确认怎么写 |

这三个实验都遵守你 `AGENTS.md` 的纪律：单次改动 < 100 行、单文件 ≤ 160 行、每步讲清「核心知识点是什么」。

### 实验顺序的理由

先做 ① 是因为它一次性解开你最多的困惑：**subagent、上下文隔离、预算、委派即工具调用**——这四个你在 alter-ego 里分不清的概念，在 30 行代码里会自然分层。做完之后再看 `DelegateRunner.run()`（68 行，你已经有了），你会发现它只是把实验里的 `history=[]` 换成了 `new TaskEngine()`，把预算换成了 `remainingRounds`。
