## 一、一句话结论

**你现在手里是一个「协议层全打通」的最小 ReAct Agent**——流式、工具调用、多轮循环这些最容易被教程讲错、也最容易踩坑的部分，你已经亲手写透并跑通了。

**真正的差距不在「会不会调用工具」，而在「怎么管理上下文、怎么规划、怎么安全地被人类监督」。** 这正是 2026 年前沿 Agent（Claude Code、Manus、Deep Agents 等）和玩具 demo 的分水岭。

**所以下一步答案很明确：先做你 `003-tasks.md` 里已经写好的「阶段 5：上下文管理」**，它现在的名字应该升级一下——**Context Engineering（上下文工程）**，这是当前 Agent 领域最核心的工程问题。

## 三、对照前沿 Agent：差距在哪

| 能力维度 | 你现在 | 前沿做法（2026） | 优先级 |
| --- | --- | --- | --- |
| **上下文工程** | 全部历史无脑累积，越聊越长直到超限 | 状态投影、历史裁剪/摘要、工具结果截断落盘、Prompt 只放「指针」、Prompt Caching | **P0（下一步）** |
| **人类监督 / HITL** | 无；且刻意禁止了 shell 工具 | 高危动作前 `_interrupt` 审批门；`read_file`/`write_file` + diff 预览 + y/n 确认 | **P0（紧随其后）** |
| **规划** | 只有 system prompt 里的文字规则 | Plan-and-Execute / `write_todos`，结构化计划存在 Agent State 而非对话历史 | P1 |
| **长期记忆** | 只有单次会话的内存数组 | 短期上下文 + 长期/情景记忆 + 选择性检索 + 记忆巩固（定期总结落盘） | P1 |
| **反思与自检** | 无；模型说完就返回 | 生成 → 对照标准批判 → 修订的 Reflection 循环；最终答案前结构化自检 | P1 |
| **工具生态** | 2 个固定工具，全量塞进 prompt | 渐进式披露（先给最小描述，按需加载详情）、工具分层、MCP 标准协议 | P2 |
| **子 Agent** | 单 Agent | 隔离上下文的 sub-agent，并行处理、防止上下文污染 | P2 |
| **给 Agent 一台计算机** | 无 | 虚拟文件系统作为「外部记忆」，大结果存文件，shell/代码执行（你目前禁止任意 shell，可以只做安全的文件工具） | P2 |
| **可观测 / 成本** | 有事件流，但没有 token 统计与轨迹文件 | 每次请求的 token 账本、trace 落盘、可回放 | P1 |

## 四、接下来学什么：具体路线

### 第 1 站（立刻做）：阶段 5 —— 上下文工程

这是你原计划里的阶段 5，也是当前最值得投入的一站。你要亲眼看到「长对话为什么变贵、变傻、最后报错」。

**拆成 4 个小 commit，每个都能单独验收：**

1. **上下文计数**：在每次 `chat()` 前统计 `messages` 的字符数/估算 token 数，通过 `step` 事件打印出来。先能「看见」增长曲线，再谈治理。
2. **工具输出截断**：长工具返回值只保留前若干字符 + 后若干字符，中间用 `…（已省略 N 字）` 代替，对应设计文档 §9 的「2000 字符上限」。
3. **历史裁剪**：超过阈值（如 12000 字符）时，**永远保留 system 消息**，从最早的 user/assistant 对开始丢弃。注意必须成对待删，否则会出现孤立的 `tool` 消息导致服务端报错。
4. **（进阶彩蛋）上下文落盘**：被裁掉的历史不要直接扔，写到 `code/.mini-agent/memory.log`，并在 system prompt 里告诉模型「需要旧信息时可以调用 `read_memory` 工具按需读回」。**这一步就是前沿的「Prompt = 指针，不是存储」思想的雏形**，做完你会对 Claude Code 为什么能跑长任务有实感。

**验收**：连续对话 20 轮后，请求体大小不再线性增长；不报 context 超限；裁剪后模型仍能记住前面说过的城市（AC-3 不回退）。

**核心知识点**：模型的「记忆」就是你手里的那个数组；上下文不是越多越好（Context Rot），Agent 的工程难题从「怎么调用模型」变成「该给模型看什么」。

### 第 2 站：阶段 6 —— 危险工具 + 权限确认（HITL）

你原计划的阶段 6，对应前沿的 Human-in-the-Loop，是「demo → 可用」的关键一跃。

- 加 `read_file` / `write_file`，路径白名单限制在项目目录内，拒绝 `../` 越界
- 写文件前打印目标摘要/diff，等用户输入 `y` 才执行
- **继续保持「不提供任意 shell 工具」这条红线**（这是你文档里最正确的安全决策之一）
- 验收：让模型「把 README 第一行改掉」，输入 `n` 后文件不应有任何变化

### 第 3 站及以后：往「对齐前沿」走的选修路线

按这个顺序加，每站都能独立学习、独立提交：

1. **规划器**：`write_todos` 工具 + Plan-and-Execute。先让模型输出一个结构化任务列表存在 state 里，再逐步执行、勾选完成。学的是「计划存在 Agent State，即使上下文被摘要掉也不丢」。
2. **反思循环**：最终回答前做一次自检（对照用户原始要求逐条 check），不满意就修订一轮。学的是「用一次额外模型调用换质量」。
3. **长期记忆 + 选择性检索**：把跨会话偏好/事实存到本地 JSON 或简单文件，下一轮开始时按相关性检索注入。不碰向量库也能学到「记忆是检索问题，不是存储问题」。
4. **工具渐进式披露**：工具多起来后，只把工具名和一句话描述放进 prompt，模型需要详情时调 `get_tool_detail`。学的是「工具描述也占上下文预算」。
5. **子 Agent**：写一个 `task` 工具，spawn 一个带干净上下文的子 agent 去查资料，只把结论回传。学的是「上下文隔离」。

**暂时不要碰**：多 Agent Swarm、MCP 协议完整实现、RAG 向量库、reasoning 流式展示。这些要么会稀释你的学习主线，要么需要引入依赖，违背你「零框架、手把手」的初衷——等前面的都吃透了，再看它们就是水到渠成。

## 五、怎么执行（贴合你的项目纪律）

你的 `AGENTS.md` 已经给了最好的节奏，照做即可：

- **一次只做一个阶段**，一个阶段一个 commit；跨越多个阶段先拆分、先问
- 每次交付必须包含三件事：改了哪些文件及为什么 / 怎么验证（输入什么、期望看到什么）/**这一步的核心知识点是什么**
- commit message 里那句「学到：xxx」坚持写下去——一年后回看，它就是你的学习笔记
- 改 `llm.ts` / `agent.ts` 核心逻辑时，在回复里解释「为什么这样改」

## 六、我对你这个项目的总体判断

**底子很扎实，方向完全正确。** 很多人学 Agent 是从装 LangChain 开始，结果框架替他做完了所有决策，他只学会了调 API；你是从裸协议开始，把 SSE 分片拼接、tool_calls 成对回传、多源降级这些真正难的东西都踩了一遍。这条路的复利很大——等你做上下文工程、规划器、HITL 时，你会发现它们都只是往同一个 `runAgent` 循环里加东西，而不是推翻重写。

**你现在缺的不是再写一个更炫的 demo，而是给这个循环装上「工程约束」**：上下文预算、人类审批、结构化状态、可观测性。这四样加上去，mini-agent 就从一个「能跑的教学玩具」变成一个「理念上真正对齐前沿 Agent 的骨架」。
