# 006 决策是如何实现的（概念深挖）

> 定位：`000-concepts.md` 的运行时续篇。000 讲「模型只生成文本」，
> 本篇讲「这段文本怎么变成 Agent 的决策」。
> 阅读前提：理解 `tool_calls` 是模型生成的文本，不是函数调用。

> 说明：文中行号对应仓库当前版本，代码演进后可能变化，请以函数名和结构为准。

## 1. 先纠正一个说法

`002-design.md` 说「`agent.ts` 只做循环 + 决策」。循环你已经知道——就是那个
`for (let step = 1; step <= config.maxSteps; step++)`。那「决策」呢？

**反直觉的结论：真正的决策者不是你的代码，是模型。`agent.ts` 里的「决策」只是「解读」模型的决定。**

展开后不到 5 行，就是 `agent.ts` 里这一句：

```ts
if (result.toolCalls.length === 0) {
  // 模型决定：不调工具了 → 收尾
  history.push({ role: 'assistant', content: result.text });
  return result.text;
}
// 否则模型决定：要调工具 → 逐个执行，结果塞回 history，下一轮再问模型
```

所以循环和决策是这样配合的：

> **`for` 循环负责给模型「反复做决策」的机会，那一行的 `if` 负责读懂模型这次决定了什么。**

---

## 2. 决策链路全景

决策不是凭空产生的。整个过程分四个环节，循环不止：

```
       ① 决策依据（你喂给模型的东西）
       SYSTEM_PROMPT + tools 菜单 + history 上下文
                        │
                        ▼
       ② 模型做决策 = 生成结构化文本
       看菜单 → 生成 text 或 tool_calls（不是函数调用！）
                        │
                        ▼
       ChatResult { text, toolCalls }
       （llm.ts 的 readStream() 按 index 把碎片拼成这个结构）
                        │
                        ▼
       ③ 代码读懂决策 = 一行 if
       result.toolCalls.length === 0 ?
          │ 是                          │ 否
          ▼                            ▼
      return text                runTool(name, args)
      循环结束                   执行 → 结果塞回 history
                                        │
                                        └──► 下一轮：模型看到新结果，重新决策（回到 ②）
                                             由 for 循环提供次数上限
```

---

## 3. 环节①：决策依据 —— 你喂给模型三样东西

模型是根据你给的材料做决定的。打开 `chat()`（`llm.ts`），请求体里就装着这三样：

```ts
const body = {
  model: config.model,
  messages,          // ← history：历史对话 + 之前工具的结果
  temperature: config.temperature,
  stream: true,
};
if (tools.length > 0) body.tools = tools;   // ← tools 菜单
```

加上 `agent.ts` 顶部的 **SYSTEM_PROMPT**（规则：涉及天气必须调工具、没说地点先定位）。
这三样合起来就是模型的「决策材料」：

| 材料 | 位置 | 作用 |
| --- | --- | --- |
| 规则 SYSTEM_PROMPT | `agent.ts` 顶部 | 告诉模型**该不该调**工具 |
| tools 菜单 | `tools.ts` 每个工具的 `description` | 告诉模型**能调哪些**、什么情况用 |
| history | 累积的 `messages` 数组 | 告诉模型**之前发生了什么** |

> 这就是 `description` 必须写清楚「什么情况下该调用我」的原因——它是写给模型看的决策依据。

---

## 4. 环节②：模型做决策 —— 生成一段结构化文本

回扣 `000-concepts.md`：模型并没有「执行」任何函数，它是**生成**了这样一段文本
（协议层约定好叫 `tool_calls`）：

```json
{ "name": "get_my_location", "arguments": "{}" }
```

意思是「我决定调这个工具、用这些参数」。流式返回时它是碎片，`llm.ts` 的 `readStream()`
按 `index` 拼起来，最终形成 `ChatResult { text, toolCalls }` 交还给 `agent.ts`。

**决策的产物就是一个数据结构，不是什么神秘的东西。**

---

## 5. 环节③：代码读懂决策 —— 一行 if

`agent.ts` 拿到这个结构后，只问一个问题：**模型这次还要不要工具？**

- `toolCalls.length === 0` → 模型决定收尾 → 返回正文，`for` 循环结束
- 否则 → 模型决定调工具 → 把 assistant 消息原样塞回历史、逐个执行工具、
  结果作为 `tool` 消息回灌（对应 `002-design.md` 的坑一、坑二）

**你的代码从不做决策，它只负责辨认模型决定了哪一种，然后执行相应的分支。**

---

## 6. 环节④：决策依据会更新 —— 这才是循环的意义

工具结果塞回 history 后，下一轮模型看到的东西变了，于是重新决策。
用「明天天气」走一遍就彻底通了：

| 轮次 | 模型看到的 history | 模型的决策 | 代码做什么 |
| --- | --- | --- | --- |
| 第 1 轮 | system 规则 + 「明天天气」 | 规则说没给地点 → 调 `get_my_location` | 执行定位，把坐标塞回 history |
| 第 2 轮 | 多了坐标 | 调 `get_weather`，带上坐标 | 执行天气查询，把结果塞回 history |
| 第 3 轮 | 多了天气数据 | 收尾，生成正文 | `toolCalls.length === 0` → 返回答案 |

**一句话总结**：决策 = 模型基于你给的规则 / 菜单 / 历史生成的 `tool_calls`（或没有）；
`agent.ts` 的「决策」= 用 `if (toolCalls.length === 0)` 读懂这个决定，要么收尾、
要么执行工具把结果喂回去让模型再决定。`for` 循环只是给这个
「决定 → 执行 → 再决定」反复发生提供次数上限。

## 7. 自查题（验证你真的懂了）

**问题**：如果模型死活不调工具、直接编一个天气出来，按上面的链路，问题最可能出在
①②③④ 哪个环节？

<details>
<summary>点开看答案</summary>

**环节①**——决策依据出了问题。环节①有三样材料：规则、菜单、历史。逐样排查：

1. **规则没进 history（最贴近「编造」症状）**：规则不是全局注入的，它是
   `createSession()` 返回数组里的第 0 条 system 消息。若外壳传的是 `[]`
   而不是 `createSession()`，tools 菜单仍在，但模型不知道「天气必须调工具、
   严禁编造」，于是有工具也不用、直接凭记忆编一个。
   **对「编造」而言这比菜单缺失更致命**：菜单缺失时模型通常说「我不知道」，
   规则缺失时模型有工具却不用，还以为自己在正常回答。
2. **历史没回填（解释「调了工具却仍编造」）**：`agent.ts` 第 64–83 行的
   `assistant(tool_calls)` 与 `tool(result)` 两条 push 必须成对。漏了 `tool`
   那条，下一轮模型看到「我要求调工具了」却看不到结果，协议层报不成对错误；
   若网关容错放过，模型会以为没拿到数据而编一个。注意：若**第一轮**就没调工具，
   回填还无从发生——所以这条解释的是第二轮才编造的情况。
3. **tools 菜单没真正传出去**：`llm.ts` 里 `if (tools.length > 0) body.tools = tools`，
   若工具列表为空或被漏掉，模型压根没看到菜单。
4. **模型名不支持工具调用**：`config.ts` 里 `LLM_MODEL` 填了一个没经过工具调用训练的模型。
   它看到 `tools` 也会无视，直接编答案——而且**程序不会报错**，最危险。

**现有代码没有这些 bug**：CLI（第 61 行、`/clear` 第 87 行）和 Web（第 19 行）
都正确用了 `createSession()`，回填也做了。它们是你自己定的红线——
**新写外壳时最容易踩的坑**。这也正是 `000-concepts.md` 强调「模型名不能乱填」、
以及调试时要盯着 `-> 调用 get_weather` 那行有没有出现的原因。
排查细节见复习速查手册的错误排查表。

</details>
