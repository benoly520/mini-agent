# 003 任务分解（Order）

> SDD 第 3 步：把设计切成能一个个独立验收的小块。
> **纪律：一次只做一件事，做完一个阶段必须能跑通并提交，再进下一个。**
> 千万不要让 AI 一次性「实现整个项目」——那样你能跑起来，但什么也学不到。

## 阶段总览

| 阶段 | 目标 | 状态 |
| --- | --- | --- |
| 0 | 跑通一次最朴素的 LLM 调用 | ⬜ |
| 1 | REPL + 流式输出 | ⬜ |
| 2 | 一个工具 + 单次调用 | ⬜ |
| 3 | Agent 循环（多轮） | ⬜ |
| 4 | 第二个工具（定位 → 天气两轮串联） | ⬜ |
| 5 | 上下文管理 | ⬜ |
| 6 | 危险工具 + 权限确认 | ⬜ |

> 当前仓库已完成的是「阶段 0~4 的最小合并版」，用于让你先看到完整效果。
> 强烈建议你**倒回去**按顺序重写一遍，每一阶段单独 commit，这才是学习路径。

---

## 阶段 0：最朴素的 LLM 调用（30 行）

**目标**：理解「调用大模型」本质上就是一次 HTTP POST。

**要写**：一个 `playground.ts`，硬编码一条 user 消息，`fetch` 打 `/chat/completions`，
`console.log` 出 `choices[0].message.content`。

**验收**：终端打印出模型的一句中文回答。

**你要回答自己的问题**：
- 请求体里 `model` / `messages` / `temperature` 各是什么？
- 响应里的 `usage.prompt_tokens` 是什么？改长 prompt 会变吗？
- 把 `apiKey` 故意改错，错误信息长什么样？

---

## 阶段 1：REPL + 流式输出

**目标**：让它变成一个可以一直聊的程序，并且是逐字出现的。

**要写**：
- `readline` 循环，`> ` 提示符
- `stream: true`，手写 SSE 解析（`002-design.md` 第 5 节的缓冲区写法）
- 先 `process.stdout.write` 逐字输出，再补一个换行

**验收**：输入「讲个 50 字的故事」，文字一个字一个字出现，不是停顿几秒后整段弹出。

**坑**：忘了 `decoder.decode(chunk, { stream: true })`，中文会乱码。

---

## 阶段 2：一个工具 + 单次调用

**目标**：亲眼看到模型「要求」调用工具。

**要写**：
- 工具注册表结构 `{ name, description, parameters, run }`
- 只做 `get_weather` 一个工具
- 请求体加 `tools: [...]`
- 收到 `tool_calls` 后 `JSON.parse(arguments)` 并执行 `run`
- 打印工具结果

**先不做循环**：拿到工具结果就 `console.log` 出来，直接结束。

**验收**：输入「北京天气」，终端打印出真实温度数字。

**坑**：这里就会遇到 `002-design.md` 第 3 节的碎片拼接问题。流式下必须按 `index` 累加。

---

## 阶段 3：Agent 循环

**目标**：这是整个项目的核心。

**要写**：
- `for (let step = 0; step < maxSteps; step++)`
- 无 `tool_calls` → 返回 `content`，循环结束
- 有 → 追加 assistant 消息 + 逐条执行工具 + 追加 tool 消息 → 继续
- 超过 `maxSteps` 强制终止

**验收**：输入「现在是几点？」，模型如果连续 5 轮都要工具，程序不卡死而是提示已达上限。

**关键自查**：把 `messages` 整个 `JSON.stringify` 打出来看一眼。
你能读懂它，就说明你真的懂了 Agent。

---

## 阶段 4：第二个工具，让循环转两圈

**目标**：制造「必须先定位、再查天气」的两轮场景，让循环真正有意义。

**要写**：`get_my_location`（先试 `ipapi.co/json/`，失败再试 `wttr.in/?format=j1`，
全失败就抛错让模型反问用户城市——**不要**退化成「读配置里的默认城市」）。

**为什么这一步很重要**：只有一轮工具调用的「循环」是假的。
加上它之后，输入「明天天气」会自然地跑 2 轮工具 + 1 轮总结，你才能看到
**上一轮的工具结果如何影响下一轮的决策**。

**验收**：`001-requirements.md` 的 AC-2。

---

## 阶段 5：上下文管理

**目标**：理解为什么长对话会「变贵、变傻、最后报错」。

**要做**：
- 统计 `messages` 总字符数，超过阈值（比如 12000 字符）时，
  从最早的 user/assistant 对开始丢弃，**但永远保留 system 消息**
- 工具返回的长文本截断到 2000 字符

**验收**：连续对话 20 轮后，请求体大小不再线性增长，程序不报 context 超限。

---

## 阶段 6：危险工具 + 权限确认（进阶，可选）

**目标**：体验真正的 coding harness（如 Claude Code / DeepSeek CLI）为什么必须有权限系统。

**要加**：`read_file` / `write_file` 工具，以及执行前的 `y/n` 确认。

**必须遵守的安全边界**：
- 路径白名单限制在项目目录内，拒绝 `../` 越界
- 写文件前先打印 diff 或目标内容摘要
- 永远不提供「执行任意 shell 命令」的工具（这是最大的安全事故来源）

**验收**：让模型「把 README 第一行改掉」，它会先弹确认，你输入 `n` 后它不会写入。

---

## 每阶段的提交规范

```
feat(stage-2): 接入 get_weather 工具，能看到模型发起的 tool_calls

- 新增 tools.ts 注册表结构
- llm.ts 支持流式 tool_calls 按 index 累加
- 学到：arguments 是分片到达的，必须 += 拼接
```

commit message 里那句「学到」比代码本身更有价值——一年后回看，它就是你的学习笔记。

## 自查清单（每阶段结束时问自己）

- [ ] 这段代码不看注释，我还能讲清楚它在干什么吗？
- [ ] 如果模型不调工具、直接瞎编，我知道去哪加日志排查吗？
- [ ] 我能不看文档，手写出 agent 循环的骨架吗？
- [ ] 这次改动里，有没有哪一行是我「抄了但没懂」的？

最后一条最重要。**抄了没懂的代码，等于没写。**
