# 000 概念前置：模型到底在做什么

> 读代码之前先建立正确的心理模型。本文不含任何实现细节。
> 如果只读一篇，读这篇。

## 1. 一句话结论

**模型只做一件事：生成文本。**

「工具调用」不是模型调用了工具，而是模型**生成了一段符合约定的文本**，
表达「我想要调用这个工具、用这些参数」。真正干活的永远是你的代码。

## 2. 一次「明天天气」到底发生了什么

不用记结论，跟着数据走一遍就明白了。整个过程是 **2 次请求、2 次响应**。

### 第 1 次请求（你的代码 → 模型）

你的代码组装出这段 JSON 发出去：

```json
{
  "model": "glm-4.5-flash",
  "messages": [
    { "role": "system", "content": "遇到天气问题必须调用工具，不要凭记忆回答" },
    { "role": "user",   "content": "明天天气" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询某地某一天的天气预报",
        "parameters": { "type": "object", "properties": { "...": "..." } }
      }
    }
  ]
}
```

`tools` 这一段是重点：**你在告诉模型「我手上有这些工具可选，它们分别干什么」**。
模型看不到 `run()` 的代码，它只看到名字、描述、参数说明——就像你拿到一份菜单。

### 第 1 次响应（模型 → 你的代码）

模型返回的是一段 **JSON 文本**（对你的代码来说就是个字符串，`JSON.parse` 之后才成为对象）：

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_1",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\":\"北京\",\"date_offset\":1}"
        }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}
```

**整篇文章的重点就在这一屏**：

- `tool_calls` 不是「模型调用了一个函数」，而是「模型吐出了一段格式约定好的文本」
- `finish_reason: "tool_calls"` 是模型在明确说：**「我没有回答你，我是在要求你替我做件事。」**
- `arguments` 还是个**字符串**，里面装的才是 JSON。所以你的代码要 `JSON.parse` 两次

### 第 2 步（你的代码独自完成，模型完全不参与）

你的代码读到 `tool_calls` 后做三件事：

1. 在 `tools.ts` 里按名字找到 `get_weather`
2. 把 `arguments` 那个字符串解析成 `{ city: "北京", date_offset: 1 }`
3. 调用它的 `run()`，里面真的 `fetch` 了 Open-Meteo，拿到字符串
   `"北京 2026-11-04：阴，5~13℃"`

**这一整步模型不知情**。它发出请求后就停住了，等你说结果。
它既不知道你有没有真的去查，也不知道查回来的是什么。

### 第 2 次请求（你的代码 → 模型）

把上面所有往返都塞回 `messages`，再发一次：

```json
"messages": [
  { "role": "system",    "content": "..." },
  { "role": "user",      "content": "明天天气" },
  { "role": "assistant", "content": null, "tool_calls": [ "..." ] },
  { "role": "tool",      "tool_call_id": "call_1",
    "content": "北京 2026-11-04：阴，5~13℃" }
]
```

注意最后那条 `role: "tool"` —— 这是**你**写的，不是模型写的。
模型是通过这条消息，才**第一次**看见天气数据。

### 第 2 次响应（模型 → 你的代码）

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "北京明天阴天，气温 5~13℃，出门记得加件外套。"
    },
    "finish_reason": "stop"
  }]
}
```

`finish_reason: "stop"` 表示「我说完了」。这次没有 `tool_calls`，循环结束。

### 打个比方

> 模型像个只能写纸条、不许离开房间的顾问。
>
> 你说「明天天气」，它写张纸条递出来：「调用 get_weather，city=北京」。
> 你拿着纸条去外面查，把结果写在另一张纸条上递回去。
> 它看了结果，写出最终回答。
>
> 它从头到尾没离开过房间，也没查过任何东西。

### 怎么判断一件事该谁做

看数据流就够了：

| 凡是需要「真实数据」的地方 | 凡是需要「判断、表达、组织语言」的地方 |
| --- | --- |
| 你的代码 | 模型 |
| `fetch` 天气、定位 IP、读文件 | 决定要不要调工具 |
| 执行工具、校验参数 | 决定传什么参数 |
| 维护 `messages` 数组 | 决定怎么说给用户听 |

模型全程**没有联网、没有执行任何函数**。它不知道 `get_weather` 内部长什么样。

## 3. 「内置」的是什么

| 内置（训练得到） | 不内置（永远做不到） |
| --- | --- |
| 理解 `tools` 参数里的 JSON Schema | 知道工具的具体实现 |
| 输出符合规范的 `tool_calls` 结构 | 访问实时数据 |
| 根据工具返回值调整下一步 | 记住上一次会话（每次都要重发全部历史） |

## 4. 这个能力是怎么来的

它不是天生的，是**专门训练出来的**：

1. **2023 年前**：只能靠 prompt 硬求「请只输出 JSON」，再用正则提取。
   模型经常加解释、加代码块、拼错字段名，极不稳定。
2. **之后**：厂商用大量「(对话, 可用工具) → 正确的 tool_call」样本做微调，
   于是有了 `tools` 参数这种原生协议。

**「支持工具调用」= 这个模型被专门训练过，能在看到 `tools` 时输出规范结构。**

## 5. 为什么不能随便换模型

因为这是额外训练出来的能力，不是语言模型天然具备的：

| 模型水平 | 给了 `tools` 参数后会发生什么 |
| --- | --- |
| 没训练过 | 完全无视，直接编一个答案给你 |
| 训练不足 | 想调但格式错，或把调用写在正文里而不是 `tool_calls` 字段 |
| 正常支持 | 正确返回 `finish_reason: "tool_calls"` + 合法 JSON |

**最危险的是第一种**：程序不会报错，只是永远不调工具、直接编造天气。
用户看到一段通顺的回答，完全不知道数据是假的。

这就是 `config.ts` 里模型名不能乱填的原因，也是为什么调试时要盯着
`-> 调用 get_weather` 这行有没有出现。

## 6. 怎么验证一个模型支不支持

发一次带 `tools` 的请求，看返回：

```bash
# 关键看这两个字段
finish_reason: "tool_calls"      ← 支持，且这次决定调用
tool_calls: [{"function": {...}}] ← 结构是否正确、参数是否合理
```

本项目实测 `glm-4.5-flash` 返回了
`{"city":"北京","date_offset":1}`，说明它确实具备这个能力。

## 7. 进阶：不依赖内置能力也能做

既然工具调用本质是「生成符合格式的文本」，理论上可以完全绕开协议：

```
System: 如果你想调用工具，请输出 {"tool":"xxx","args":{...}}
模型返回普通文本 → 你自己正则解析 → 执行 → 把结果塞回 messages
```

早期项目都这么干。但代价是：
- 解析极不稳定（模型爱加解释、爱加 markdown 包裹）
- 无法保证调用顺序，无法并行
- 各家格式互不统一

`tools` 参数是协议层的进步：把「格式约束」从 prompt 工程变成了模型能力。
你在 `llm.ts` 里只是加了一行 `body.tools = tools`，背后是厂商在训练阶段做的事。

## 8. 对应到本项目的代码

```
config.ts / .env      模型名必须选支持工具调用的
      ↓
llm.ts                请求体里带上 tools: [...]        ← 「告诉模型有哪些工具」
      ↓
模型                  返回 tool_calls                  ← 「模型表达调用意图」
      ↓
agent.ts              解析、执行、把结果塞回 messages  ← 「循环在这里」
      ↓
tools.ts              真正发 HTTP、拿真实数据          ← 「唯一真正干活的地方」
```

## 9. 三个常见误解

**「模型能上网查天气」**
不能。它只能生成文本。数据是 `tools.ts` 通过 `fetch` 拿到的。

**「模型记得我们聊过什么」**
不记得。模型是无状态的，每次请求都要把完整 `messages` 重新发一遍。
「记忆」是你手里的那个数组，不是模型的能力。

**「temperature 调高会让它更聪明」**
不会。temperature 只影响输出随机性。工具调用场景要**调低**（本项目用 0.3），
让它稳定地选对工具和参数，而不是发挥创意。

## 10. 一句话总结

> Agent 的智能在模型里，Agent 的能力在你的代码里。
> 模型说「我想做什么」，你的代码决定「能不能做、怎么做」。
